1. Executive Summary (Deliverable 01)

1.1 What Was Investigated

Over the course of this assignment, the analytical foundation, telemetry footprint, data quality, and financial accounting readiness of the VELOOP Rewards ecosystem were comprehensively audited. The investigation examined: * The 15 distinct user-facing modules currently simulated across the platform (Missions, Watch Ads, Tap & Earn, Mining Rewards, Daily Rewards, Streak Rewards, Badges, Level System, Spin the Wheel, CAPTCHA, Follow & Earn, Exchange Center, Wallet, Leaderboard, Referrals). * The 15 workbook tabs provided in the official Google Drive repository (VELoop_Rewards_Data_01.xlsx and VELOOP_Simulated_User_Behavior_1000.xlsx), containing 1,000 user profiles, 7,913 closed sessions, 35,704 clickstream events, 9,846 task activity attempts, and 6,667 daily activity rollups. * The end-to-end data lifecycle from client-side event emission, ingestion buffering, relational schema modeling, and double-entry financial accounting through to executive BI consumption.

1.2 What Was Discovered

  1. Pristine Relational Joins on Existing Simulated Tables: Automated join scripts confirmed 0 orphan records across existing tables (Sessions.user_id $\rightarrow$ Users.user_id, Events.session_id $\rightarrow$ Sessions.session_id, Tasks.user_id $\rightarrow$ Users.user_id). The simulation maintained perfect foreign key consistency.
  2. Critical Financial & Architectural Gaps:
  3. No Transaction Ledger: In the simulated behavior sheets, wallet activity exists only as a UI click event (wallet_viewed) or an aggregated boolean flag. There is zero double-entry ledger table (fact_wallet_transactions).
  4. No Withdrawal Lifecycle Table: Despite cash-out being the primary customer value proposition, the simulated sheets contain zero records for withdrawal requests, processing, or settlements (fact_withdrawals).
  5. Severed Referral Attribution: Users possess referral codes, but there is no relational entity mapping the referring user to the acquired referee across registration and first-task activation.
  6. Intentional Data Quality Defects Uncovered:
  7. Users_Messy_Audit contained 16 duplicate user records (8 pairs) and a corrupted record (VLUSR000023) with a null registration date despite having 9 lifetime sessions and 210 XP.
  8. 10_Event_Data_Quality_Audit contained 20 duplicate event records (10 pairs), unstandardized lowercase feature names (missions, daily reward, wallet), and trailing whitespace in event_status ('success '), which silently drops records in standard SQL equality filters.

1.3 What is Currently Unknown (To Be Verified)

As cataloged in the Assumption & Verification Register (Work Package S): * Whether the live production backend currently emits real-time event streams or writes directly to MySQL. * Whether third-party ad networks (AdMob, Unity) provide verifiable HMAC SHA-256 signatures on S2S postbacks to prevent bot callback spoofing. * The exact timeout and sliding-window rules enforced for mobile session JWT tokens. * Whether the payment gateway (Stripe/PayPal/Cashfree) automatically retries bounced payouts or requires explicit API re-dispatch.

1.4 What VELOOP Should Implement

VELOOP must implement the Shift-Left Data Architecture established in this blueprint: 1. Pre-Launch Engineering Controls: * Enforce client-generated UUIDv4 idempotency_keys on all mutation events with a 30-minute Redis deduplication buffer. * Deploy the immutable double-entry ledger schema (fact_wallet_transactions) and withdrawal state machine (fact_withdrawals). * Enforce database PRIMARY KEY and UNIQUE constraints to eliminate Cartesian join bugs. * Instrument the standardized [entity_object]_[action] event catalogue across client and backend microservices. 2. Data Pipeline & Operating Model: * Deploy a cost-effective Serverless Lakehouse ($< \$250/mo$) using Google Cloud Storage, dbt Core, and BigQuery, avoiding expensive $\$5k+/mo$ Kafka/Spark clusters. * Automate daily double-entry ledger balancing queries: $\sum \text{Credits} - \sum \text{Debits} == \sum \text{User Balances}$. 3. Privacy & Governance: * Implement column-level dynamic data masking in the warehouse, replacing raw emails with SHA-256 hashes and domain rollups to comply with GDPR and DPDP mandates.

1.5 Major Risks & Prioritized Mitigations

  • Risk 1: Duplicate Financial Payouts from Network Retries.
  • Mitigation: API Gateway Redis deduplication buffer + database unique constraint on idempotency_key (Priority: Critical).
  • Risk 2: Unmonitored Financial Liabilities & Ledger Drift.
  • Mitigation: Append-only transaction ledger with atomic running_balance_after verification and hourly automated drift alarms (Priority: Critical).
  • Risk 3: Regulatory Fines from Plaintext PII Ingestion.
  • Mitigation: Shift-left PII exclusion; store payment vault tokens and hashed identifiers rather than raw account credentials (Priority: High).
  • Risk 4: Referral Farming & Bot Ring Exploitation.
  • Mitigation: 4-stage referral qualification gate requiring referees to complete at least 1 monetizable task before advocate bonuses are unlocked (Priority: High).

Gap 1: Absence of a Double-Entry Transaction Ledger Table

  • Issue: In the current simulated behavior dataset, wallet interactions are only represented as a UI event (wallet_viewed) or an aggregated daily counter (wallet_activity). There is no immutable transaction ledger table (fact_wallet_transactions).
  • Consequence: Impossible to audit point-in-time user balances, calculate token velocity, perform financial reconciliation, or detect ledger drift/unauthorized balance inflation.
  • Priority: Critical
  • Remediation: Implement a backend double-entry ledger table tracking transaction_id, user_id, transaction_type (Credit/Debit/Reversal/Adjustment), amount, currency_unit, reference_id, and running_balance.

Gap 2: Complete Absence of a Normalized Withdrawal Lifecycle Entity

  • Issue: The dataset contains no records for withdrawal requests, processing pipelines, or payout outcomes (fact_withdrawals), despite withdrawal being the core value-proposition of a rewards app.
  • Consequence: Management cannot evaluate payout SLA, gateway failure rates, rejection distributions, or outstanding liquidity liabilities.
  • Priority: Critical
  • Remediation: Introduce a dedicated withdrawals table tracking the full finite state machine: Requested -> Under Review -> Processing -> Completed / Rejected / Reversed.

Gap 3: Severed Referral Attribution Linkage

  • Issue: The Users table contains referral_code and referral_source_detail, but there is no relational entity mapping the referring user_id to the referred user_id and tracking conversion milestones.
  • Consequence: VELOOP cannot calculate viral coefficient ($K$-factor), referral ROI, or identify referral fraud (e.g. self-referral farming).
  • Priority: Critical
  • Remediation: Establish fact_referral_conversions with referral_id, referrer_user_id, referee_user_id, attributed_code, registration_at, first_task_completed_at, and reward_credited_at.

Gap 4: Missing Task Validation & Fraud Detection Telemetry

  • Issue: 05_Task_Activity only records whether a task was Completed or Failed, with rudimentary failure reasons. There is no trace of system validation events (e.g. IP velocity checks, ad callback cryptographic signatures, CAPTCHA confidence scores).
  • Consequence: Inability to distinguish between genuine user drop-off and systematic bot exploitation; impossible to measure false-positive rates of security rules.
  • Priority: Critical
  • Remediation: Emit structured system validation events (task_validation_passed, task_validation_failed) capturing validation rule IDs, risk scores, and third-party callback payloads.

Gap 5: Lack of Event Deduplication Keys & Idempotency Tokens

  • Issue: The messy events sheet (10_Event_Data_Quality_Audit) revealed duplicate event rows with identical timestamps and IDs. Raw events lack client-generated idempotency keys (client_request_uuid).
  • Consequence: Network retries cause double-counting of completions, duplicate reward distributions, and corrupted KPI reporting.
  • Priority: High
  • Remediation: Enforce client-generated UUIDv4 idempotency_key on all mutation events and establish a deduplication window at ingestion.

Gap 6: Inconsistent Feature & Event Naming Standardization

  • Issue: Audit revealed mixed-case feature names in event streams (missions vs Missions, daily reward vs Daily Reward, watch ads vs Watch Ads).
  • Consequence: SQL aggregations with GROUP BY feature_name split single features into multiple distinct categories, distorting engagement reporting unless manual cleaning is performed.
  • Priority: High
  • Remediation: Enforce strict snake_case naming conventions (domain_object_action) at the API gateway validation layer, rejecting non-conforming payloads.

Gap 7: Granular Onboarding Funnel Telemetry is Missing

  • Issue: The user table records only a static boolean / enum onboarding_status: Completed. There are no intermediate step-by-step events (onboarding_step_viewed, onboarding_permission_prompted, onboarding_skipped).
  • Consequence: Product teams cannot pinpoint where during the critical first 3 minutes new users experience cognitive overload or churn.
  • Priority: High
  • Remediation: Instrument granular onboarding step events with sequence indices and duration-per-step tracking.

Gap 8: Conflation of "Activity Occurred" with "Reward Credited"

  • Issue: In several task events, completion is assumed to immediately equal reward distribution. However, asynchronous ad networks and affiliate task walls frequently delay, reject, or claw back payouts.
  • Consequence: Financial discrepancies between operational activity volume and true balance liability.
  • Priority: High
  • Remediation: Explicitly decouple client action telemetry (task_completed) from backend accounting events (reward_credited, reward_pending, reward_reversed).

Gap 9: Raw Storage of Unsanitized PII in Analytical Layers

  • Issue: The clean user table stores raw full_name and email alongside analytical metrics without pseudonymization or data classification tags.
  • Consequence: Severe compliance and data privacy exposure (GDPR / DPDP Act violation) if analyst workspaces access unmasked personally identifiable data.
  • Priority: High
  • Remediation: Mask/hash PII in the analytics layer, exposing only synthetic user_id and hashed identifiers to BI and analytics environments.

Gap 10: Missing Session Timeout & Heartbeat Instrumentation

  • Issue: 02_Sessions provides session_start and session_end, but lacks periodic heartbeat pings or foreground/background state indicators.
  • Consequence: Inability to distinguish between users actively engaging with the UI vs users leaving the application open in a background tab or suspended mobile state.
  • Priority: Medium
  • Remediation: Implement 30-second client heartbeat telemetry and explicit app_backgrounded / app_foregrounded state events.

Detailed Identifier Specifications:

1. Stable User Identifier (user_id)

  • Format: UUID v4 or prefixed alphanumeric string (e.g., VLUSR000001 in simulated data; standardizing to UUID v4 in production target usr_7f8c12e4-6a8b-4b11-9f93-018263549210).
  • Generation Engine: Backend Authentication Service (Primary Key of dim_users).
  • Why It Is Needed:
  • Serves as the single immutable anchor connecting all user actions across devices, platforms, web views, and mobile sessions.
  • Ensures that profile updates (e.g. email change, username change) do not sever historical behavioral longitudinal analysis or retention cohort tracking.
  • Integrity Rule: Must never change over the user's lifetime; must never contain unmasked PII (phone number, raw email).

2. Session Identifier (session_id)

  • Format: Unique alphanumeric string (e.g., SESS0000001 in simulated data; target format ses_<user_id_prefix>_<timestamp_epoch>_<random_hex>).
  • Generation Engine: Frontend SDK / API Gateway at session inception.
  • Why It Is Needed:
  • Defines the bounded temporal window of continuous user engagement.
  • Allows calculation of critical product metrics: session duration, events per session, feature traversal paths, and bounce rates.
  • Decouples raw event volume from engagement frequency (e.g. 50 events across 1 session vs 50 events across 10 distinct sessions).
  • Session Boundary Rules:
  • Inactivity Timeout: 30 minutes of client inactivity closes the session.
  • Midnight Rollover: A session crossing midnight (00:00 UTC) is closed and a new session spawned to ensure accurate Daily Active User (DAU) reporting.

3. Event Identifier (event_id)

  • Format: Globally Unique Identifier (e.g., EVT00000001 in simulated data; target format ULID: Universally Unique Lexicographically Sortable Identifier).
  • Generation Engine: Client Analytics SDK at telemetry emission point.
  • Why It Is Needed:
  • Provides atomic point-in-time identification for every logged interaction.
  • Guarantees idempotent ingestion and deduplication: network retries or client buffering flushes that resend the same event payload will not cause duplicate event counts in BigQuery/Snowflake.
  • Enables chronological ordering across distributed systems with sub-millisecond precision.

4. Transaction Identifier (transaction_id)

  • Format: High-entropy cryptographic string (target format tx_wall_<timestamp>_<uuid>).
  • Generation Engine: Backend Wallet Service / Ledger Engine.
  • Why It Is Needed:
  • Required for strict double-entry ledger accounting and financial auditability.
  • Distinguishes client telemetry (event_id: task_completed) from backend balance mutation (transaction_id: tx_12345).
  • Enables zero-loss reconciliation, rollback traceability, dispute resolution, and audit trail validation for every balance credit, debit, or clawback.

3. D2. Withdrawal Lifecycle Architecture

A withdrawal represents a real-world financial liability settlement. It must be modeled as a strict, finite state machine tracking every transition, automated gate, and gateway callback.

Detailed Lifecycle Transitions:

  1. Withdrawal Requested: User initiates payout. The requested amount is immediately debited from available balance and placed into an escrow hold to prevent double-spending.
  2. Under Review: High-value payouts, rapid velocity triggers, or accounts with elevated risk scores ($\ge 75.0$) are routed to an internal operations dashboard.
  3. Processing: The payout payload is formatted and dispatched via API to the third-party payout provider (Stripe, PayPal, Cashfree, Crypto RPC node).
  4. Completed: Asynchronous webhook from payout provider confirms that funds successfully settled into the beneficiary account.
  5. Rejected: Request terminated prior to gateway dispatch due to suspicious activity, invalid payout details, or compliance sanctions. Escrow funds returned to user wallet.
  6. Reversed: External banking network or gateway rejects transfer post-dispatch (e.g. closed bank account, invalid routing code). Escrow hold converted into a formal REVERSAL ledger credit.

1. Feature Adoption & Penetration

  • Metric: Feature Penetration Rate ($\%$)
  • Formula:
    $$\text{Penetration}_{\text{feature}} = \frac{\text{Unique Users Engaging with Feature in Window } T}{\text{Total Active Users (AU) in Window } T} \times 100$$
  • Simulated Benchmark (from 07_Feature_Usage):
  • Top Engaged Features: Watch Ads ($83.6\%$), Daily Reward ($83.5\%$), Streak Rewards ($83.2\%$).
  • Mid-Tier Features: Missions ($77.1\%$), Spin the Wheel ($76.3\%$).
  • Under-Adopted Features: Follow & Earn ($68.5\%$), Badges ($67.4\%$).
  • Analytical Value: Identifies which features drive initial utility vs features suffering from discoverability friction.

2. Repeat Usage & Habit Formation

  • Metric: 7-Day Habitual User Percentage ($L7 \ge 4$)
  • Formula:
    $$\text{Habitual User Ratio} = \frac{\text{Count of Users with } \ge 4 \text{ Active Days in Rolling 7-Day Window}}{\text{Total WAU}} \times 100$$
  • Analytical Value: Isolates core habitual earners from opportunistic visitors.

3. Task Velocity & Engagement Depth

  • Metric: Completed Tasks per Active User Day ($CTPD$)
  • Formula:
    $$CTPD = \frac{\sum \text{completed_task_count}}{\sum \mathbf{1}_{{\text{active_flag} = \text{'Yes'}}}}$$
  • Simulated Baseline: Mean session count is $1.14$ sessions/day; mean completed tasks per record is $0.78$ tasks/day (with heavy power users reaching up to 38 completed tasks in a single day).

4. Active vs. Returning User Segmentation

To monitor platform vitality, users are segmented dynamically on any given calendar day $D$:

User Cohort Definition Business Importance
New Active User (NAU) First qualifying activity event occurs on Day $D$ ($\text{activity_date} = \text{registration_date}$). Measures top-of-funnel acquisition health.
Retained Active User (RAU) Active on Day $D$ and was also active on Day $D-1$. Measures short-term day-over-day stickiness.
Resurrected User (ReAU) Active on Day $D$ after being dormant for $\ge 14$ consecutive days. Measures effectiveness of re-engagement pushes.
Dormant User (DU) Zero activity events for $14\text{--}29$ consecutive days. High churn risk; trigger lifecycle win-back campaigns.
Churned User (CU) Zero activity events for $\ge 30$ consecutive days. Base attrition; excluded from active reporting pools.

5. Platform Stickiness Ratio (DAU / MAU)

  • Formula:
    $$\text{Platform Stickiness} = \frac{\text{Daily Active Users (DAU)}}{\text{Monthly Active Users (MAU)}} \times 100$$
  • Interpretation: Measures how frequently monthly active users return to the app. In rewards and casual gaming apps, a DAU/MAU ratio of $20\%\text{--}30\%$ represents solid engagement; $> 40\%$ represents best-in-class daily utility.

Proposed Standard: [entity_object]_[action] (Lowercase snake_case)

After evaluating alternatives (domain_object_action vs object_action), VELOOP standardizes on the [entity_object]_[action] convention.

  • Pattern: <noun>_<past_tense_verb> (e.g., user_registered, task_completed, reward_credited, withdrawal_requested).

  • Elimination of Redundant Stutter: Domain-prefixed naming creates unnecessary verbal clutter in telemetry (e.g., wallet_withdrawal_withdrawal_requested or earning_task_task_completed). Under our standard, the domain is captured cleanly in the feature_domain metadata field.
  • Direct Alignment with Industry Best Practices: Conforms to the standard semantic event specifications utilized by Segment, Snowplow, RudderStack, and Google Analytics 4.
  • Self-Documenting Code: Developers can instantly deduce what occurred: the object operated on and the state reached.

1. Architectural Modeling Principles

The VELOOP logical data model is architected following an enterprise Dimensional Hybrid Schema (Kimball Star-Snowflake hybrid with an append-only event log and a double-entry financial ledger).

Design Objectives:

  1. Financial Immutability: Financial ledger entries (fact_wallet_transactions) and payout settlements (fact_withdrawals) are strictly append-only. State changes generate compensating or transition rows rather than in-place updates.
  2. High-Throughput Telemetry: Clickstream events (fact_feature_events) are decoupled from transactional databases to prevent analytical queries from impacting transactional performance.
  3. Idempotent Referential Integrity: Every fact table is linked to persistent dimension tables via immutable surrogate and business keys (user_id, task_id, session_id).

5. H3. Detailed Relationship Documentation

1. One-to-One ($1:1$) Relationships:

  • dim_users to fact_referral_conversions (as Referee): A newly registered user (referee_user_id) can be acquired through at most one referral relationship. (A user cannot be referred by multiple advocates).
  • fact_task_activity to fact_wallet_transactions: For a completed, validated task attempt (activity_id), there is at most one corresponding REWARD_CREDIT ledger transaction. The ledger's reference_id maps $1:1$ back to activity_id.

2. One-to-Many ($1:N$) Relationships:

  • dim_users to dim_sessions ($1:N$): A single user initiates multiple continuous interaction sessions over their platform lifetime.
  • dim_users to fact_feature_events ($1:N$): A user generates thousands of clickstream and feature interaction events.
  • dim_users to fact_wallet_transactions ($1:N$): A user accumulates multiple credit, debit, exchange, and adjustment ledger records.
  • dim_users to fact_withdrawals ($1:N$): An active earning user can request multiple cash-outs over time.
  • dim_users to fact_referral_conversions (as Referrer) ($1:N$): A successful advocate user (referrer_user_id) can refer multiple new referees.
  • dim_tasks to fact_task_activity ($1:N$): A single catalog task definition (e.g. TASK0071) is attempted thousands of times by different users.
  • dim_sessions to fact_feature_events ($1:N$): A single session encapsulates all events executed between session_start and session_end.

3. Many-to-Many ($M:N$) Relationships:

  • dim_users to dim_tasks ($M:N$ via fact_task_activity): Users attempt many tasks, and each task is attempted by many users. The bridge entity fact_task_activity resolves this into two $1:N$ relationships.
  • dim_users to dim_badges ($M:N$ via fact_user_badges): Users earn multiple badges, and badges are minted to multiple users. Resolved by fact_user_badges.

4. Event & Transaction Relationships:

  • Telemetry Event to Transactional Ledger Boundary:
  • Telemetry events (fact_feature_events) capture untrusted client activity (task_completed, withdrawal_requested).
  • Ledger entries (fact_wallet_transactions) capture trusted server-side double-entry balance mutations.
  • They are connected loosely via reference_id and idempotency_key, preventing race conditions and keeping high-throughput clickstream data separate from immutable financial ledgers.

2. Domain 1: User Lifecycle KPIs

KPI 01: Daily Active Users (DAU)

  • Definition: The count of unique authenticated users who generate at least one qualifying telemetry interaction event within a 24-hour UTC calendar day.
  • Formula:
    $$\text{DAU}t = \text{COUNT}(\text{DISTINCT } \text{user_id}) \quad \forall \; \text{event_datetime} \in [t]$$}}, t_{\text{23:59:59}
  • Required Fields: fact_feature_events.user_id, event_datetime.
  • Data Source: fact_feature_events (or fact_daily_user_summary where active_flag = 'Yes').
  • Frequency: Daily.
  • Stakeholder: Executive Leadership, Head of Product.
  • Business Purpose: Core barometer of platform scale and daily engagement reach.
  • Interpretation: Sustained day-over-day growth signals healthy product-market fit; sharp contractions highlight outages or app store visibility drops.
  • Limitation: Does not distinguish between passive single-tap users and highly active multiple-task earners.
  • Status: Confirmed.

KPI 02: Weekly Active Users (WAU)

  • Definition: The count of unique authenticated users who generated at least one qualifying activity event in the trailing 7 rolling calendar days.
  • Formula:
    $$\text{WAU}_t = \text{COUNT}(\text{DISTINCT } \text{user_id}) \quad \forall \; \text{event_datetime} \in [t - 6\text{d}, t]$$
  • Required Fields: fact_feature_events.user_id, event_datetime.
  • Data Source: fact_feature_events.
  • Frequency: Weekly (computed daily on a rolling 7-day window).
  • Stakeholder: Product Management, Growth Team.
  • Business Purpose: Smooths weekday/weekend volatility to track medium-term user reach.
  • Interpretation: Upward trend indicates strong weekly habituation across casual earners.
  • Limitation: Insensitive to mid-week churn if the user was active on Day 1 of the 7-day window.
  • Status: Confirmed.

3. Pipeline Component Specifications

1. Source Systems & Event Producers

  • Client SDKs (Android, iOS, Web): Emits client-side behavioral events (task_viewed, task_started, task_completed, spin_started). Automatically enriches payloads with device, app version, and session metadata.
  • Core Backend Microservices: Emits transactional and state-change events (user_registered, reward_credited, streak_updated, withdrawal_requested).
  • Third-Party Partner Webhooks: Receives asynchronous completion postbacks from ad networks (AdMob), survey routers (BitLabs), and payout gateways (Stripe, PayPal).

2. Collection & Ingestion Layer

  • Technology: Serverless API Gateway + Managed Queue (GCP Pub/Sub or AWS SQS).
  • Throughput Capacity: Scalable from 10 events/sec to 10,000+ events/sec without provisioning physical servers.
  • Ingestion Dedup Buffer: Managed Redis instance checks idempotency_key and event_id within a 30-minute sliding window to absorb mobile client network retry storms.

3. Raw Storage Layer (Bronze Lake)

  • Technology: Google Cloud Storage (GCS) or AWS S3.
  • Format: Raw, uncompressed/snappy-compressed append-only JSON files partitioned by date and hour (gs://veloop-lake-raw/year=2026/month=11/day=01/hour=12/).
  • Dead-Letter Queue (DLQ): Payloads failing JSON parsing or schema validation are automatically routed to gs://veloop-lake-dlq/ for developer inspection and replay.

4. Validation & Transformation Layer (Silver Layer)

  • Technology: dbt Core (data build tool) running automated SQL transformations against BigQuery / Snowflake.
  • Execution Frequency:
  • Near-Real-Time Stream: Micro-batch streaming into staging tables every 5 minutes.
  • Hourly Transformations: Re-indexes operational tables (fact_withdrawals, fact_task_activity).
  • Daily Aggregations: Generates analytical marts at 01:00 UTC.
  • Quality Assurance Gate: Every dbt run executes 40+ automated integrity tests (unique, not_null, relationships, non-negative numeric constraints). If any critical assertion fails, downstream updates are halted and an alert is dispatched.

5. Analytical Data Layer (Gold Layer)

  • Technology: Partitioned and clustered columnar tables in Google BigQuery (or PostgreSQL with TimescaleDB for ultra-low-budget deployments).
  • Table Partitioning Strategy:
  • fact_feature_events: Partitioned by DATE(event_datetime), clustered by feature_name, user_id.
  • fact_wallet_transactions: Partitioned by DATE(transaction_timestamp), clustered by currency_unit, transaction_type.
  • fact_withdrawals: Partitioned by DATE(requested_timestamp), clustered by withdrawal_status, payout_method.
  • Cost Efficiency: Clustering eliminates 85% of query byte scans, keeping BigQuery query costs negligible ($< \$30/mo$).

6. BI & Dashboard Consumption Layer

  • Technology: Looker Studio (free tier to start) or Metabase (open-source self-hosted on a \$20/mo VM).
  • Refresh Schedule:
  • Executive Cockpit: Cached hourly; manual refresh available.
  • Withdrawal Operations Monitor: Auto-refreshes every 15 minutes.
  • Retention Cohort Matrix: Refreshes daily at 03:00 UTC.

4. Operating Model, Monitoring & Failure Handling

1. Pipeline Monitoring & Health Observability:

  • Metric Freshness Monitor: Alert triggers if the gap between current time and the most recent event partition exceeds 30 minutes.
  • Data Volume Drift Detection: Automated SQL monitor flags if daily event volume drops by $> 30\%$ or spikes by $> 150\%$ compared to the 7-day rolling average.
  • Ledger Reconciliation Alert: Hourly cron tests: $$\sum \text{Credits} - \sum \text{Debits} == \sum \text{User Balances}$$ If variance is non-zero, an emergency P0 Slack alert is fired to Finance and Engineering Leads.

2. Failure Handling & Disaster Recovery:

  • Replay Protocol: If transformation bugs are introduced, the immutable Bronze Lake allows complete historical replay. The dbt pipeline can be wiped and re-executed from raw storage (dbt run --full-refresh).
  • DLQ Replay Tool: A simple Python CLI script (replay_dlq.py) re-submits patched payloads from the DLQ back into the ingestion gateway.
