### 1. Executive Purpose & Engineering Contract

The **Developer Analytics Handoff** is the authoritative implementation document for software engineers, QA automation engineers, and data platform developers. It translates product analytics objectives into **testable, unambiguous technical requirements**.

#### Core Implementation Rules:
1. **Idempotency Standard:** Every client-emitted event must supply an `idempotency_key` (UUIDv4) generated at the moment the action occurs. API gateways must deduplicate retries within a 30-minute sliding window.
2. **Atomic Ledger Guarantees:** Financial ledger transactions must execute within an ACID database transaction. Telemetry events for monetary balance updates must only be emitted **after** a successful database commit.
3. **Automated Test Coverage:** Each event includes an explicit, automated Acceptance Test criteria that must pass in staging before deployment.

#### Requirement ID: REQ-EVT-001
* **Event Name:** `user_registered`
* **Trigger:** Auth Service successfully creates a new persistent record in `dim_users` following form submission or OAuth callback.
* **Source:** Backend Auth Microservice
* **Timestamp Standard:** ISO 8601 UTC timestamp generated by backend database clock (`CURRENT_TIMESTAMP`).
* **Why Needed:** Foundational root event for cohort retention analysis, customer acquisition attribution, and growth accounting.
* **KPI Dependency:** Total Registrations (NRU), CAC, Channel Conversion Rate, D1/D7/D30 Retention.
* **Priority:** **Critical (P0)**

##### Payload Schema:
| Field | Data Type | Required? | Validation Rule | Deduplication Standard |
|---|---|---|---|---|
| `event_id` | String (ULID) | Yes | 26-char alphanumeric ULID | Unique PK |
| `user_id` | String (UUID) | Yes | Regex: `^usr_[a-zA-Z0-9_\-]+$` | Unique PK in `dim_users` |
| `timestamp` | Timestamp | Yes | ISO 8601 UTC; $\le \text{Current Time}$ | Immutable |
| `registration_channel` | String | Yes | Allowed values: `Organic`, `Referral`, `Paid Ads`, `Social`, `Direct` | Whitelist enum |
| `referral_code_used` | String | No | Nullable; if present, must match active code | Nullable |
| `auth_provider` | String | Yes | Allowed values: `EMAIL`, `GOOGLE`, `APPLE` | Whitelist enum |
| `client_version` | String | Yes | Semantic versioning format `^v?[0-9]+\.[0-9]+\.[0-9]+$` | Standard SemVer |

##### Acceptance Test:
> **GIVEN** a new user completes the registration form with valid credentials,  
> **WHEN** the user account is committed to the database,  
> **THEN** exactly one `user_registered` event must be published to the event bus with non-null `user_id`, matching `registration_channel`, and zero PII (no raw passwords or unhashed emails).

#### Requirement ID: REQ-EVT-002
* **Event Name:** `user_logged_in`
* **Trigger:** Auth Service verifies credentials, refreshes session tokens, and issues an active JWT.
* **Source:** Backend Auth Microservice
* **Timestamp Standard:** ISO 8601 UTC timestamp at JWT generation.
* **Why Needed:** Required to compute DAU, WAU, MAU, session frequency, and active user retention.
* **KPI Dependency:** Daily Active Users (DAU), Monthly Active Users (MAU), Platform Stickiness ($DAU/MAU$).
* **Priority:** **Critical (P0)**

##### Payload Schema:
| Field | Data Type | Required? | Validation Rule | Deduplication Standard |
|---|---|---|---|---|
| `event_id` | String (ULID) | Yes | Unique ULID string | Unique PK |
| `user_id` | String (UUID) | Yes | Foreign key to `dim_users` | Valid user reference |
| `session_id` | String | Yes | Regex: `^ses_[a-zA-Z0-9_\-]+$` | Unique session token |
| `timestamp` | Timestamp | Yes | ISO 8601 UTC | Immutable |
| `auth_method` | String | Yes | Allowed: `PASSWORD`, `BIOMETRIC`, `REFRESH_TOKEN`, `SSO` | Whitelist enum |
| `is_first_login` | Boolean | Yes | Boolean (`true` / `false`) | Evaluates if session count == 1 |

##### Acceptance Test:
> **GIVEN** an existing registered user authenticates successfully,  
> **WHEN** the authentication response is returned with HTTP 200,  
> **THEN** exactly one `user_logged_in` event must be emitted containing the newly provisioned `session_id` and the user's immutable `user_id`.

#### Requirement ID: REQ-EVT-003
* **Event Name:** `task_completed`
* **Trigger:** Client confirms that user has satisfied task criteria (video watched, survey submitted, game score attained).
* **Source:** Frontend Client SDK / Partner Webhook Router
* **Timestamp Standard:** ISO 8601 UTC timestamp at client completion.
* **Why Needed:** Primary operational event tracking earning activity, user velocity, and task conversion.
* **KPI Dependency:** Task Completion Rate (TCR), Task Starts vs Completions, Mean Time-to-Complete.
* **Priority:** **Critical (P0)**

##### Payload Schema:
| Field | Data Type | Required? | Validation Rule | Deduplication Standard |
|---|---|---|---|---|
| `event_id` | String (ULID) | Yes | Unique ULID string | Unique PK |
| `activity_id` | String | Yes | Regex: `^ACT[0-9]{7}$` | Unique task attempt key |
| `user_id` | String (UUID) | Yes | Foreign key to `dim_users` | Valid user reference |
| `task_id` | String | Yes | Foreign key to `dim_tasks` | Valid task reference |
| `session_id` | String | Yes | Foreign key to `dim_sessions` | Valid session context |
| `timestamp` | Timestamp | Yes | ISO 8601 UTC | Client timestamp |
| `duration_seconds` | Integer | Yes | $\ge$ minimum task duration threshold | Must be positive |
| `client_proof_token` | String | Yes | Cryptographic HMAC signature from client SDK | Non-empty |
| `idempotency_key` | String | Yes | UUIDv4 generated by client at completion | Deduplicated at gateway |

##### Acceptance Test:
> **GIVEN** an active user initiates a rewarded task,  
> **WHEN** the required action is validated on client/gateway,  
> **THEN** exactly one `task_completed` event is emitted. Network retries with the same `idempotency_key` must be acknowledged with HTTP 200 but dropped from analytical ingestion.

#### Requirement ID: REQ-EVT-004
* **Event Name:** `reward_credited`
* **Trigger:** Core Wallet Service successfully commits an atomic balance increment in the double-entry transaction ledger.
* **Source:** Backend Wallet Microservice
* **Timestamp Standard:** ISO 8601 UTC timestamp from the database ledger commit clock.
* **Why Needed:** Represents legal financial liability issuance and point-in-time balance accumulation.
* **KPI Dependency:** Gross Reward Issuance Volume, Cost of Rewards, XP Velocity.
* **Priority:** **Critical (P0)**

##### Payload Schema:
| Field | Data Type | Required? | Validation Rule | Deduplication Standard |
|---|---|---|---|---|
| `event_id` | String (ULID) | Yes | Unique ULID string | Unique PK |
| `transaction_id` | String | Yes | Regex: `^tx_wall_[0-9]+_[a-f0-9]+$` | Unique PK in `fact_wallet_transactions` |
| `user_id` | String (UUID) | Yes | Foreign key to `dim_users` | Valid user reference |
| `amount` | Decimal(18,4)| Yes | Numeric $> 0.0000$ | Positive value |
| `currency_unit` | String | Yes | Whitelist: `XP`, `GEMS`, `TOKENS` | Whitelist enum |
| `source_module` | String | Yes | Whitelist: `WATCH_ADS`, `SURVEY`, `SPIN`, `REFERRAL`, `STREAK` | Whitelist enum |
| `reference_id` | String | Yes | Originating business key (`activity_id`, `referral_id`) | Non-null |
| `running_balance_after`| Decimal(18,4)| Yes | $\text{Previous Balance} + \text{amount}$ | Exact mathematical balance |

##### Acceptance Test:
> **GIVEN** a verified task completion or milestone unlock,  
> **WHEN** the wallet service writes to the database,  
> **THEN** the balance update must be committed atomically with an updated `running_balance_after`, and exactly one `reward_credited` event must be published referencing the unique `transaction_id`.

#### Requirement ID: REQ-EVT-005
* **Event Name:** `daily_reward_claimed`
* **Trigger:** User taps "Claim" on daily reward dialog and backend validates that no claim has occurred for the current UTC date.
* **Source:** Backend Gamification Service
* **Timestamp Standard:** ISO 8601 UTC timestamp at claim verification.
* **Why Needed:** Measures habit-loop execution and day-over-day engagement continuity.
* **KPI Dependency:** Daily Claim Rate, Streak Retention, D7/D14/D30 Retention.
* **Priority:** **High (P1)**

##### Payload Schema:
| Field | Data Type | Required? | Validation Rule | Deduplication Standard |
|---|---|---|---|---|
| `event_id` | String (ULID) | Yes | Unique ULID string | Unique PK |
| `user_id` | String (UUID) | Yes | Foreign key to `dim_users` | Valid user reference |
| `session_id` | String | Yes | Foreign key to `dim_sessions` | Valid session context |
| `calendar_day_number` | Integer | Yes | Range: 1 to 30 | Day index in monthly calendar |
| `streak_day_count` | Integer | Yes | Monotonically increments previous active streak | Integer $\ge 1$ |
| `reward_amount` | Decimal | Yes | Standard daily reward tier value | Numeric $> 0$ |
| `reward_unit` | String | Yes | Whitelist: `XP`, `GEMS`, `TOKENS` | Whitelist enum |

##### Acceptance Test:
> **GIVEN** an active user who has not yet claimed their daily reward on calendar date $D$,  
> **WHEN** they submit a claim request,  
> **THEN** the claim is verified, streak counter incremented, reward posted, and exactly one `daily_reward_claimed` event emitted. A second claim attempt on date $D$ must be rejected with HTTP 409.

#### Requirement ID: REQ-EVT-007
* **Event Name:** `withdrawal_requested`
* **Trigger:** User submits external cash-out request; funds debited to escrow hold.
* **Source:** Backend Payout Gateway Service
* **Timestamp Standard:** ISO 8601 UTC timestamp upon request receipt.
* **Why Needed:** Captures cash-out intent and gross liquidity liability demand.
* **KPI Dependency:** Gross Withdrawal Request Volume & Count, Liquidity Run Rate.
* **Priority:** **Critical (P0)**

##### Payload Schema:
| Field | Data Type | Required? | Validation Rule | Deduplication Standard |
|---|---|---|---|---|
| `event_id` | String (ULID) | Yes | Unique ULID string | Unique PK |
| `withdrawal_id` | String | Yes | Regex: `^WD_[0-9]+$` | Unique PK in `fact_withdrawals` |
| `user_id` | String (UUID) | Yes | Foreign key to `dim_users` | Valid user reference |
| `requested_amount` | Decimal(10,2)| Yes | $\ge 5.00$ (Minimum cash-out threshold) | Positive value |
| `payout_currency` | String | Yes | Whitelist: `USD`, `INR`, `EUR` | Whitelist enum |
| `tokens_debited` | Decimal(18,4)| Yes | Matches redemption rate for requested amount | Positive value |
| `payout_method` | String | Yes | Whitelist: `PAYPAL`, `BANK_TRANSFER`, `UPI`, `CRYPTO_USDT` | Whitelist enum |
| `destination_hash` | String | Yes | 64-char SHA-256 hash of destination | Masked PII hash |

##### Acceptance Test:
> **GIVEN** an active user with verified balance $\ge \text{requested\_amount}$ and $\ge \$5.00$,  
> **WHEN** they submit the payout form,  
> **THEN** the balance is debited to escrow, withdrawal record is created in `REQUESTED` status, and exactly one `withdrawal_requested` event is emitted.

#### Requirement ID: REQ-EVT-008
* **Event Name:** `withdrawal_completed`
* **Trigger:** Asynchronous webhook from external payment gateway (Stripe, PayPal, Cashfree) confirms beneficiary settlement.
* **Source:** Backend Payout Webhook Consumer
* **Timestamp Standard:** ISO 8601 UTC timestamp from gateway confirmation webhook.
* **Why Needed:** Marks terminal cash outflow settlement and fulfills user payout SLA.
* **KPI Dependency:** Completed Withdrawals (Volume & Count), End-to-End Payout SLA Latency.
* **Priority:** **Critical (P0)**

##### Payload Schema:
| Field | Data Type | Required? | Validation Rule | Deduplication Standard |
|---|---|---|---|---|
| `event_id` | String (ULID) | Yes | Unique ULID string | Unique PK |
| `withdrawal_id` | String | Yes | Foreign key to `fact_withdrawals` | Must match existing request |
| `user_id` | String (UUID) | Yes | Foreign key to `dim_users` | Valid user reference |
| `settlement_amount` | Decimal(10,2)| Yes | Exactly matches net approved amount | Positive value |
| `processing_fee` | Decimal(10,2)| Yes | Network gateway fee absorbed | $\ge 0.00$ |
| `total_sla_duration_hours`| Decimal | Yes | $\text{settlement\_time} - \text{requested\_time}$ | Must be positive |
| `gateway_reference_id`| String | Yes | External payment rail transaction ID | Non-null |

##### Acceptance Test:
> **GIVEN** a withdrawal in `PROCESSING` state dispatched to an external gateway,  
> **WHEN** a cryptographically verified success webhook is received,  
> **THEN** withdrawal status transitions to `COMPLETED`, escrow hold is formally cleared, and exactly one `withdrawal_completed` event is emitted.
